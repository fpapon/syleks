# P00 — Syleks capability audit and baseline

Audit date: 2026-10-25. Source baseline: `982d89624e07f63c09fad9d4f57346157d5a132e` (the initial working tree was clean).

This is a source and fixture audit, not a production-provider certification or a security penetration test. No application implementation, configuration, dependency, or test was changed. Build output and isolated test/smoke data were generated. No inference service was invoked with repository content. Official documentation was consulted using public protocol terms and URLs only.

## Location, authorization, and evidence rules

Before creating this file, the audit checked the root `AGENTS.md`, the existing `docs/README.md` and audit directories, and searched for additional `AGENTS.md` files. Only the root instructions applied. `docs/` resolves to this checkout's ordinary documentation directory; neither `docs/engineering` nor the target file existed, and neither was a symlink. The user's P00 instruction explicitly requests this exact Markdown artifact. Together these checks establish an appropriate, authorized location without overwriting manual work. Existing `docs/audits/security/` and `docs/audits/opencode-parity/` remain untouched.

In the tables, **implemented** means a concrete source path exists; **partial** means useful foundations exist but the engineering requirement is not fully met; **absent** means no dedicated implementation was found in production source, SQL migrations, configuration schema, or the inspected tests. Named tests are evidence of their particular scenarios, not guarantees for all deployments. Verification outcomes and limits appear below.

Class names use package suffixes under `fr.openobject.ai.syleks`. For example, `ai.AgentRuntime` is [`src/main/java/fr/openobject/ai/syleks/ai/AgentRuntime.java`](../../src/main/java/fr/openobject/ai/syleks/ai/AgentRuntime.java); `session.SubagentExecutionTest` is [`src/test/java/fr/openobject/ai/syleks/session/SubagentExecutionTest.java`](../../src/test/java/fr/openobject/ai/syleks/session/SubagentExecutionTest.java). All test names below refer to actual source classes and methods.

## Actual platform and architecture

[`pom.xml`](../../pom.xml) declares one Java 25 Maven module, Fusion **1.2.0**, JLine **3.30.3**, SQLite JDBC **3.53.2.0**, JUnit Jupiter **5.13.4**, Nimbus JOSE JWT **10.10**, and networknt JSON Schema validator **1.5.1**. Fusion dependencies are `fusion-api`, `fusion-cli`, `fusion-build-api`, `fusion-processor`, and `fusion-json`. Build API and processor dependencies are provided scope; annotation processing generates application wiring. Spotless **3.10.4** uses Google Java Format **1.30.0**, AOSP style. Surefire is **3.6.0**; Shade is **3.6.2**.

The agent engine, SQLite repositories, MCP client, authentication, and usage services are application code. There is no declared Fusion AI, workflow, SQLite, or MCP module to assume. Current extension work can use the demonstrated Fusion 1.2.0 APIs: `@DefaultScoped`, `@ApplicationScoped`, constructor/injected dependencies, `@Init`/`@Destroy`, `ConfiguringContainer`, and `JsonMapper`. Any additional Fusion module/API needs separate version-specific inspection before adoption. JSON Schema validation also uses Jackson transitively; this is not a Fusion-only JSON stack.

`app.Main` routes CLI commands and starts Fusion; `tui.TerminalApp` owns terminal output. `ai.ChatSession` coordinates synchronized state and generation workers; `session.AgentService` owns persistent generation and context maintenance. `provider.ProviderService` selects/checks routing; transport adapters use `ai.AgentRuntime` for model/tool rounds. `ai.ToolExecutor` applies validation, gates, and effects; `ai.SubagentExecutor` creates persisted child work through the same runtime. This is substantially broader than the root `AGENTS.md` description of an Ollama terminal chat application.

## Confidentiality, provider verification, and material risks

1. **Project policy can expand an agent's authority.** `PermissionPolicy.overlay` appends rules, and the last match wins. `AgentCatalog` loads project Markdown without the MCP project's explicit trust mechanism. Ancestor intersection cannot repair authority already broadened in every effective ancestor. This is source-confirmed behavior, also exercised by the merge test; P00 did not execute an exploit. Prioritize [SEC-01](../audits/security/01-permission-ceiling-and-project-trust.md).
2. **A local process or “Local” label does not prove local inference.** `AppConfig` falls back to loopback Ollama, but [`defaults/agent-config.json`](../../src/main/resources/defaults/agent-config.json), installed by `ConfigInitializer`, selects `local/qwen3.8-27b` at `http://192.168.52.32:8000/v1`. This is a LAN HTTP endpoint classified non-local by the provider policy, not proof of on-device computation. The README's general loopback-default statement needs this setup-template distinction. Per-agent model overrides can also change the destination. P00 inspected routing code/templates, not the user's private configuration, server, proxy, DNS, or packet traffic; actual deployment inference location remains unverified.
3. **`allow_cloud=false` is not a process-wide network sandbox.** `ProviderService` checks provider operations, with an early return for hosts classified local. Web requests (`AgentTools`), shell commands, MCP initialization/invocation, authentication and arbitrary Java extensions use independent paths. Proxy configuration and a loopback forwarding server can separate the apparent endpoint from the actual destination. A model-editable project policy file is not a user-owned immutable egress ceiling. See [SEC-06](../audits/security/06-network-destinations.md) and [SEC-03](../audits/security/03-command-sandbox.md).
4. **Allowed bash has normal OS authority and most inherited environment variables.** `LocalCommandRunner` removes Bash startup/function/option hooks; it does not clear unrelated credentials or impose filesystem/network isolation. MCP stdio has a tighter environment allowlist but the same OS authority. Shell output and approved read/tool results become model context. See [SEC-02](../audits/security/02-subprocess-environment.md).
5. **Approvals are useful but broader than an engineering review gate.** Always grants cover all targets for an agent/operation in the app session. Native multi-step plans are not transactional, custom extensions are trusted code, and an approved MCP server can have broader effects than a displayed schema. Existing [SEC-05](../audits/security/05-scoped-approvals.md) and [SEC-09](../audits/security/09-approval-display.md) remain proposals, not implemented guarantees.
6. **Private data persists.** SQLite, exports, file journal before/after contents and tool history can contain confidential code or secrets. POSIX private file modes are not encryption. `CredentialStore` can use a vault but has a protected plaintext fallback; custom provider keys and literal MCP configuration can also be plaintext. Dedicated credential records are excluded from session archives, but secrets pasted into conversation/tool content are not magically removed. See [storage and privacy](../storage-and-privacy.md) and [SEC-08](../audits/security/08-secret-storage.md).
7. **Estimation and summarization have limits.** Byte-based admission is approximate; configured response reserve does not impose a universal provider output cap. Responses request construction deliberately omits unsupported plan-route sampling/output-limit fields. Summarization can lose critical detail, run several requests, and send historical content to the selected provider. Raw local history remains available, but no root token/cost cap currently bounds that work.
8. **Build warnings and documentation drift deserve follow-up.** Packaging reports overlapping shaded resources/classes, including Fusion JSON classes; build success alone does not establish that all duplicates are harmless. The root project description is outdated. Existing audit/backlog documents are historical/proposed evidence, not proof of current implementation or live compatibility.

### Official ChatGPT protocol cross-check

On 2026-10-25 the audit searched official OpenAI documentation and opened [Registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) and [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference). The published flow describes dynamic issued-client registration, a stable host identifier, loopback callback, PKCE/state/nonce, identity validation and an explicit plan-usage scope. These correspond to the inspected authentication classes; identity alone must not authorize inference.

The inference contract describes account-specific catalog selection and eligible streamed Responses requests using `store: false`, with success established by terminal completion. These correspond to `ResponsesLlmProvider` and its fixtures. This establishes a documented integration path, not eligibility, quota, model availability, or successful billing for any actual account. No live login, API key, subscription inference, or account catalog was used. Other adapters were inspected as implementations; P00 makes no new external compatibility claim for them.
