# ADR 0001: Engineering documents and an opt-in runtime boundary

Date: 2026-10-25. Status: **Proposed — awaiting human approval of the public contract**.

## Context

The approved [P00 audit](../AUDIT.md) establishes Java 25, Fusion 1.2.0, application-owned agent/MCP code, SQLite schema 6, a mature TUI, and important gaps between conversation persistence and engineering workflows. Project agent definitions can expand effective permissions. Endpoint names and loopback addresses do not establish inference locality. Existing tool approval is not artifact release approval.

P01 needs reviewable contracts and enforceable confinement without implementing a scheduler, workflow execution, budget ledger, repository analyzer, or release engine. Framework and skill content belongs to a separate template repository, whose location was not supplied; this change does not clone or modify any such repository.

## Proposed decisions

1. **Use versioned JSON as the initial module interface.** The packaged [v1 schema](../../../src/main/resources/engineering/contracts-v1.schema.json) defines eight discriminated document types and a user-owned project registry. Every object has an explicit `kind` and integer `schema_version`. Unknown fields/versions fail closed. Native Java public model/service interfaces are deferred until approval and an actual integration consumer exists. `EngineeringDocuments` and `TechnologyPackLoader` are package-private implementations. `EngineeringBoundary` and `AppConfig.engineering()` are internal cross-package wiring, not supported plugin interfaces.
2. **Separate project enrollment, template data, and execution authority.** Enrollment is explicit in the user's `~/.config/syleks/engineering-projects.json`, outside every enrolled project. Its project roots apply to descendants, including delegated work. Local packs use absolute paths, a semantic version and an exact SHA-256 pin of `pack.json`; its entries each carry a content digest. Read-only loading produces bounded immutable text snapshots. Framework/skill/workflow instances stay in the external template checkout; Syleks contains their schema/reader, not a built-in engineering framework or installer. No external references, executable hooks, automatic downloads or credential fields exist in the contract.
3. **Protect enrolled projects at actual dispatch boundaries.** `ProviderService.stream`, both legacy `OllamaClient` turn preparation and HTTP send, and `ResponsesLlmProvider.chat`/send enforce the boundary. This covers tool continuations, child model overrides and compaction requests. `ToolExecutor` checks before registry resolution and again before execution; MCP discovery and authentication are also gated. In P01, potentially external tools (`bash`, web tools, MCP, custom Java tools) are denied for enrolled projects. Existing native file/skill/todo/question/task tools still require their ordinary permissions. All returned tool output remains inside the project boundary and is rechecked before the next LLM send.
4. **Require reviewed local routing; defer cloud release.** Engineering inference accepts only an exact user-reviewed provider/endpoint pair on literal `127.0.0.1` or `[::1]`, with no configured or implicit system proxy. The user must establish that the listener actually performs local inference without forwarding. The program does not infer this from a display name or hostname. A pinned loopback route is a user attestation, not network/backend attestation; process isolation against a hostile listener remains future work. Engineering cloud inference stays blocked in P01 even when `allow_cloud=true`, because there is no trusted exact-payload release executor. `allow_cloud=false` can never be overridden by an approval, a pack, or a release reference.
5. **Limit future permitted cloud inference to documented subscription adapters.** The only audited subscription integration is `chatgpt`, using its existing official sign-in, scope, account catalog and Responses completion checks. API-key providers, arbitrary OpenAI-compatible endpoints, Google/Anthropic OAuth assumptions, OpenCode subscriptions and foreign OAuth tokens are not alternatives. P01 does not change authentication, move tokens between accounts/adapters, or enable cloud execution. A later cloud release adapter must still use `ProviderService`/`ChatGptLlmProvider` and existing account/model/scope checks; a generic HTTP endpoint cannot consume those credentials.
6. **Keep private provenance immutable through authorized release.** A derived artifact can have private inputs and an authorized outbound representation. The context entry retains `provenance: PRIVATE`; `release_id` is only a reference. Parsing `APPROVED` in an `ApprovalGate`, public output text, a summary, a question answer, or an imported session does not confer authority. A future user-owned release record must bind exact outbound bytes/digest, original context lineage, project/run/stage, destination, action, policy revision, expiry and reviewer identity. Any changed bytes or destination require new authorization. The project cloud ceiling and provider eligibility remain separate mandatory checks.
7. **Preserve existing storage and terminal interfaces.** No session table, archive shape, provider interface, `ChatRequest`, `ToolContext`, `CustomTool`, CLI option, shortcut or terminal rendering contract changes. New workflow state storage is specified but not created in P01. Existing code outside enrolled projects retains its permissions and provider behavior; there is no claim of retrofitting a global OS sandbox.

## Runtime mechanics and consequences

The enrollment file is parsed once per `AppConfig`, with a SHA-256 snapshot. It is bounded and rejects duplicate keys, malformed UTF-8, symlinks, unknown versions/fields and excessive nesting. Active pack manifests/resources are verified during enrollment. At each inference/tool dispatch the registry must still exist with exactly the same bytes; additions, edits and removal require a restart and cannot relax a running session. A missing registry preserves legacy operation, but creating one mid-session also requires restart. Content from a project cannot enroll itself or approve its route. Ordinary project cloud policies and `SYLEKS_ALLOW_CLOUD` still apply through the existing provider service and can only further restrict inference.

No pack resource is inserted into current chat context, installed as an agent/skill, or executed. Existing `.syleks/skills` behavior remains separate. The loaded snapshot is the pack reader's integration result for future Engineering consumers. There are no workflow run transitions, approval decisions, reservations or analysis jobs in P01.

This deliberately limits Engineering functionality: shell builds, network tools and cloud models cannot run in an enrolled project yet. The TUI still opens, renders, edits prompts, navigates sessions and displays refusals. A future reviewed release/effect gateway must replace this conservative denial with an equally enforceable boundary before those actions can be enabled. An `allow_cloud=true` value is permission to consider a release, not a bypass or a guarantee of cloud availability.

## Storage, errors, cancellation, and compatibility

The [contract guide](../CONTRACTS.md) defines document responsibilities, lifecycle invariants, storage mapping and error codes. The [compatibility note](../COMPATIBILITY.md) records opt-in behavior and limitations. SQLite remains schema 6; a future approved migration must introduce project/run/artifact/gate/context/budget/analysis records transactionally, using existing `SqliteDatabase`/`DataPaths` and project-scoped repository conventions. Authority stays outside project-editable data and imported archives. There is no silent schema downgrade or replay of uncertain effects.

Validation and loading check thread interruption, bound input/allocations and preserve the interrupted flag. Dispatch uses the existing cancellation, session leases and child ancestry. No credentials/source content are included in validation diagnostics. Existing typed tool outcomes carry denials; invalid enrollment fails startup closed.

## Alternatives considered

- Adding configuration fields and agent/skill definitions to bundled defaults would couple independent packs to Syleks releases and let project data appear authoritative. A separately pinned local template checkout avoids that coupling.
- Trusting `ProviderCapabilities.local()` or the word Local would accept forwarding servers and overlook proxies. Exact user-reviewed routing plus direct connections is more explicit, while remaining honest about the absence of backend attestation.
- Defining a complete public Java workflow SPI before its consumer would freeze speculative methods and execution semantics. Strict JSON interfaces and package-private parsers allow review of the eight data contracts first.
- Allowing cloud when a project or imported JSON says Approved would confuse provenance with authority. P01 denies it until a user-owned exact-payload release path exists.
- Refactoring all permission/security backlogs or introducing an OS sandbox now would expand P01 beyond module contracts. The opt-in boundary is intentionally narrower and does not supersede the audit backlog.

## Approval requested

Approve or amend these public contract decisions before treating schema v1 as stable: **(A)** the nine JSON kinds and strict integer-version policy; **(B)** user-owned project enrollment plus version/hash-pinned local template packs; **(C)** conservative runtime denial of external tools/cloud until an authorized release gateway exists, with reviewed direct loopback inference only; **(D)** immutable private provenance, separately bound release approval, and deferred SQLite workflow storage. Java implementations may change internally; no public workflow engine API is approved by this ADR's proposed status.

Validation evidence is recorded in [P01 validation](../P01-VALIDATION.md). No merge, publication, deployment, template repository change or permission expansion is part of this proposal.
