# P01 compatibility note

Status: proposed contract, pending the human approval requested in [ADR 0001](adr/0001-engineering-contracts.md).

No `engineering-projects.json` means legacy behavior. Existing `agent-config.json` and its JSON Schema, project agent precedence, skills, permission panels, file edits, subagent tasks, persisted chats, session archives, usage accounting, provider logins, selection, compaction, editor, rendering, shortcuts and CLI routing keep their existing contracts. Session SQLite schema remains **6**. No new Fusion dependency or module is introduced; Java remains 25 and Fusion remains 1.2.0. `ChatRequest`, `ToolContext`, `LlmProvider` and `CustomTool` signatures are unchanged. No workflow engine or public Java workflow SPI is introduced.

The new schema's JSON kinds are deliberately **proposed**, with strict parsing rather than silently ignored fields. There is no automatic migration into Engineering mode and no bundled engineering framework/skill content. Loading an external pack does not replace current agents, skills or project instructions. Existing examples remain valid. Startup reads only the user's own enrollment path, never an arbitrary project-provided enrollment file.

Enrollment changes behavior deliberately for a project and its descendant launch directories. Native file/skill/todo/question/task tools remain subject to existing permissions. Shell, web, MCP discovery/invocation/authentication and arbitrary custom tools are denied; cloud inference is denied until a future trusted release gateway exists. Local inference requires an exact reviewed literal-loopback route with direct networking. The TUI remains usable and reports the refusal through existing error/tool outcomes; no new modal or terminal thread is added. Config changes require restart; removal cannot release an already enrolled running session.

A local endpoint name or the existing Local badge is not evidence of local inference. The existing setup template's LAN HTTP endpoint is **not** automatically approved for Engineering data. Users must verify that an approved loopback listener performs inference locally without forwarding. No new claim of OS isolation, protection against malicious in-process Java code, local server compromise, same-user filesystem races, encrypted storage, sanitized prompt history, or safe publication follows from enrollment.

Changing a valid shared registry, even for another project, invalidates its running `AppConfig` snapshot and requires restart at the next dispatch. Invalid registry data fails startup rather than reverting to legacy behavior. A registry present but listing only other roots leaves the current project unenrolled. API-key/cloud providers remain available for such legacy projects under their existing policy; subscription-only routing applies to Engineering's future authorized cloud path.

For developers: use the schema resource and package-private parser/pack reader for validation. `EngineeringBoundary` and the new `AppConfig.engineering()` accessor are internal wiring across packages; their public Java visibility is not a plugin compatibility promise. Public integration should use the proposed JSON interface only after human approval. Future changes to schema shape require a new `schema_version`; semantic pack updates require new version/digest pins, without repurposing existing OAuth tokens or silently changing providers.

Automated compatibility evidence includes the existing full suite and the new contract/boundary/loopback tests; exact outcomes are in [P01 validation](P01-VALIDATION.md). No terminal UI code was changed, and manual real-terminal testing remains a separate unperformed check.
