# Token usage

Syleks collects consumption from actual LLM responses and stores it with the active SQLite session. The right sidebar appears when the terminal has at least 105 columns and 20 rows. It reserves 32 columns, leaving at least 69 usable columns for the conversation and prompt. Short terminals show a compact summary. `/usage` opens the complete, scrollable view at any width; Esc closes it without changing the prompt or conversation scroll.

## Commands and preferences

- `/sidebar` toggles visibility and saves the preference.
- `/sidebar auto` shows the sidebar when the terminal has enough room (default).
- `/sidebar show` requests visibility, subject to the same safe size constraints.
- `/sidebar hide` always hides it.
- `/usage` displays session totals, context, the last invocation, performance, and totals grouped by provider and model. Arrow keys and PgUp/PgDn scroll this modal.

Preferences share the existing provider selection file, `$XDG_CONFIG_HOME/syleks/config.json` (otherwise `~/.config/syleks/config.json`). Writes use the existing configuration lock and atomic replacement, preserving provider/account selections. For example:

```json
{
  "sidebar": "AUTO",
  "context_warning_percent": 70,
  "context_critical_percent": 90
}
```

Merge these keys into the existing file; do not replace account or model settings. Threshold changes take effect after restart. They must satisfy `0 <= warning < critical <= 100`. The context bar is cyan below warning, orange from warning through critical, and red above critical. No new keyboard shortcut is reserved.

## Reading the numbers

| Metric | Meaning |
| --- | --- |
| Input | Tokens processed as input, including resent history, instructions and tool results |
| Output | Tokens generated by the provider, potentially including reasoning |
| Total | Provider total, or input plus output for Ollama when both are known |
| Cached | Input tokens read from a provider cache, when reported; a subset of input |
| Reasoning | Reasoning output tokens, when reported; a subset of output |
| Requests | Individual HTTP invocations, including tool continuation rounds and failed/interrupted attempts that reached the transport |

Cached and reasoning tokens are **never added again** to the total. `N/A` means unknown, while `0` is a known zero. `*` marks an aggregate with missing contributions; its numeric part is the known subtotal. `~` marks estimated contributions if an integration supplies them. The built-in collectors do not estimate token counts. Counters use Java `long`; overflow is displayed as unavailable/partial rather than wrapping. Formatting (`1.2K`, `1.4M`) never changes stored values.

The last request is reset to `RUNNING`/Generating at the start of each HTTP invocation, while confirmed session consumption remains visible. Exact counters are pending during streaming. A text fragment, SSE event or JSON object is never treated as one token. On failure or cancellation, Syleks preserves metrics actually received; missing metrics remain unknown. There is no inferred cost or billing estimate. A ChatGPT subscription is separate from paid OpenAI API usage.

## Configured request budget

`/usage` shows the active model's configured context window, response reserve, and input allowance (`window - reserve`). Instructions, conversation history and tool schemas share the input allowance. Admission uses a conservative UTF-8 estimate; these configuration ceilings are separate from provider-reported token counts and do not measure the next prompt's live occupancy. Primary chat automatically summarizes older exchanges near the configured threshold; progress notices show estimated input occupancy before and after compaction. Summary requests count toward session usage. `/compact` also remains available. Set `compaction.mode` to `manual` to disable automatic summary requests.

Long provider/model values wrap in the detail view. Use arrows, PgUp/PgDn, Home/End and Esc to navigate and close it; page size follows the terminal height.

## Context is different from session consumption

**Cumulative session tokens are not the tokens currently occupying the model's context window.** History can be sent repeatedly, so session consumption can exceed the context capacity many times.

Syleks currently displays the input token count of the **last completed request sent to the active provider/model**, explicitly labeled “Last sent input”. This is a historical measurement, not a live count of the next prompt, nor a count that includes the assistant answer received since that request. An in-progress, failed or interrupted last request invalidates its context token count; a known capacity may still be shown. A differently modeled or absent last request invalidates both. A new/forked session has no measured context yet, even if its conversation history is nonempty.

For Ollama, capacity is the effective `num_ctx` that Syleks puts into the persistent request, using the existing context settings (`SYLEKS_CONTEXT_WINDOW` or model `limit.context`). For Responses and compatible servers, capacity is shown only when an explicit model `limit.context` is configured. This is the operator-declared budget, not a capacity inferred from the model name. A generic fallback context budget is not presented as a discovered cloud model capacity. Catalogs in this repository do not expose authoritative effective context metadata; there is no hardcoded 128K/200K default or approximate tokenizer.

Percentage is `last_input / capacity * 100` only when both are known and capacity is positive. The bar is capped at 100%; numeric percentages can exceed 100%. Remaining tokens are `max(0, capacity - last_input)`. Unknown inputs/capacities give `N/A`.

## Provider collection and performance

[Ollama chat](https://docs.ollama.com/api/chat) reports usage in its terminal `done=true` NDJSON object. Syleks reads `prompt_eval_count`, `eval_count`, optional `prompt_eval_cached_count`, `total_duration`, `prompt_eval_duration`, and `eval_duration`. Durations are nanoseconds. Provider generation speed is `eval_count / (eval_duration / 1e9)` only for a strictly positive generation duration. Reasoning token counts are not inferred from the thinking text.

[OpenAI Responses streaming events](https://developers.openai.com/api/reference/resources/responses/streaming-events) can carry `response.usage` in terminal events. The shared Responses transport used by the existing ChatGPT and OpenAI API providers reads input/output/total, cached input details and reasoning output details from completed, incomplete and failed responses. Incomplete/failed invocations have `FAILED` status even when some consumption is available. Endpoint/account access still depends on the existing authentication and provider restrictions; this feature adds no new subscription endpoint or authorization.

Configured Chat Completions servers are asked for `stream_options.include_usage`; trailing usage events are consumed before `[DONE]`. Servers that finish with `finish_reason` followed by EOF remain supported. Compatibility depends on the server accepting that option and reporting usage; unknown metrics remain `N/A`.

“Total client” measures elapsed request/stream time with a monotonic clock. “First useful (client)” measures time from send until the first nonempty text, reasoning or function fragment. It is not an exact provider token timestamp. Provider total, prompt evaluation and generation durations are persisted separately. The full view shows provider total and generation duration when available. Speed is labeled **provider** when computed from a positive provider generation duration, otherwise **client** when computed from reported output tokens and client elapsed time. No provisional speed is inferred from fragment counts.

## Storage, sessions, retries and events

Migration `V003__llm_usage.sql` upgrades the existing database to version 3 in the existing migration transaction. `llm_usage` references `sessions(id)` with `ON DELETE CASCADE` and has an index on `(session_id, created_at)`. It stores nullable 64-bit counters, usage quality, status, client timings, provider nanosecond timings and the context budget. It contains no prompts, outputs or credentials. Database location, WAL mode, busy timeout and short transaction handling are unchanged.

A UUID identifies each transport attempt independently of message IDs. Tool continuation calls receive new IDs. There are no automatic inference retries added by this feature. Future retries must create a fresh invocation UUID if they make another HTTP attempt; replaying the same usage event retains the same ID. Upserts accept a transition from `RUNNING` to a terminal state once, ignore subsequent duplicates/stale starts, and never add the same invocation twice. Attempts with real reported consumption count even when they fail. Abandoned `RUNNING` rows become `INTERRUPTED` only while holding the existing session lease; another process's live invocation is not recovered.

The usage service publishes immutable events to subscribers and caches immutable per-session snapshots. JDBC writes and reloads run on generation/session workers, never on the rendering thread. There are two usage writes per normal invocation (start and terminal), not one per fragment. Aggregation keeps known subtotals and partial/estimated markers independently for each metric and groups totals by provider and model. Current aggregation reads the session's usage rows; extremely large histories may benefit from incremental aggregation later.

Opening/resuming a session reloads its metrics; process restarts retain the last invocation and counters. New sessions start at zero. Forks copy conversation history through the existing session mechanism but **do not copy usage rows**; new consumption belongs only to the fork. Changing provider/model keeps session totals and invalidates unrelated context measurements.

The existing 70 ms terminal loop reads cached snapshots and uses differential row painting. Statistics change at invocation boundaries, not at every text fragment. Resize and sidebar toggling rewrap messages and preserve the visible message/text anchor and editor caret. `/usage` has independent scrolling.

## Precision and validation limits

Providers can omit all or part of usage, especially on disconnect/cancellation. Syleks cannot recover unreported exact counts and does not manufacture them. Counts already available are persisted at terminal handling; a hard crash between provider completion and the final database write can leave an interrupted/unknown invocation. No historical usage can be reconstructed for conversations created before this migration. There is no project-wide `/usage project` view, new tokenizer, live next-prompt tokenization or billing integration.

Automated tests exercise simulated provider streams, terminal cell buffers, SQLite migration/reopen/idempotency/cascade/fork/concurrency, and interrupted request recovery without a live model server. Real provider access, model availability and visual behavior on a user's terminal require a separate live check.

## Configure budgets from examples

The [full configuration](../examples/agent-config.json) shows per-model `limit.context` / `limit.output`, global/per-agent `max_rounds`, and shared `subagents` execution ceilings. These fields belong in `agent-config.json`; sidebar visibility and color thresholds belong in the separate provider-selection `config.json` above. See the [complete field reference](configuration.md#complete-configuration-reference).

The example Reviewer has a 10-round agent limit under the common 16-round child ceiling, so it can use at most 10 rounds. A child configured with `max_rounds: -1` is still capped by shared child limits and the root's remaining durable round budget. Root `/usage` includes descendants, including when a specialist selects another provider. Execution ceilings do not reserve a fixed number of tokens or guarantee a cost cap.
